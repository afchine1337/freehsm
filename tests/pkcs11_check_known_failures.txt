# RSA PKCS#1 v1.5 decryption of a malformed ciphertext returns CKR_OK and
# pseudo-random bytes. That is OpenSSL's implicit rejection, the Marvin-attack
# countermeasure, and it is deliberate: an error return here is the oracle.
# 0.2.3 recognises it in TestInvalidOperations::test_decrypt_garbage, now an
# xfail; this structured-oracle test still records CKR_OK on its v1.5 samples
# as accepted_invalid. See docs/PKCS11_CHECK_FINDINGS.md. Upstream:
# mingulov/pkcs11-check#37, follow-up in #49.
# CKM_RSA_PKCS decryption exists only in all-mechanisms builds.
all-mechanisms  pkcs11_check/testcases/security/test_padding_oracle.py::TestRSAPaddingOracle::test_pkcs1v15_bleichenbacher_structured_oracle

# Key pair generation asking CKA_SENSITIVE=FALSE for the private key. A
# private key in FreeHSM is always sensitive, and since 2.7.0 (f900d10, #33)
# a template that asks otherwise is refused with CKR_TEMPLATE_INCONSISTENT
# (PKCS#11 v3.2 4.1.1) where it used to be accepted and overridden. These
# tests fail at C_GenerateKeyPair, before what they are about:
#   * test_kem.py and ckr/test_ckr_kem.py: their ML-KEM key pair helpers send
#     the attribute, and no test in them reads the private value;
#   * the RSA-OAEP cross-verification needs the private key in the clear, to
#     decrypt outside the module. It cannot run against this module; before
#     2.7.0 it reached read_rsa_private_key_or_xfail and was an xfail.
# The refusal is the module's stated behaviour (RELEASE_v2.7.0.md), so these
# are the harness's to adapt. Measured on 2026-11-12 at 8684b7e, pkcs11-check
# 0.2.3, both profiles, the same 28 in each. Upstream:
